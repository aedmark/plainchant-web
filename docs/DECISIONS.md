Newest at the bottom. To reverse a decision, add a new entry that supersedes it; the old one keeps its text and only

## D-001 Zero-build vanilla JS frontend with classic scripts and UMD modules (2026-11-02, status: accepted)
**Context:** Plainchant Web is a spinoff of Plainchant (`aedmark/plainchant`) designed as an HTML5, CSS, and JS WYSIWYG studio (P1-01, P4-01).
**Decision:** Keep Plainchant's zero-build, zero-runtime-dependency frontend architecture: pure logic lives in UMD modules under `src/*.js` (so Node tests can `require()` them directly without a bundler) and UI wiring lives in classic `<script>` files under `src/app/*.js` sharing a single global scope loaded by `app.html`.
**Alternatives:** Vite/Webpack + React/Svelte (rejected: adds build steps, bundler complexity, and breaks direct `file://` / static-server simplicity).
**Consequences:** Every file in `src/app/*.js` must stay at or under 500 lines and avoid duplicate top-level identifier declarations, enforced by `test/structure.test.js`.

## D-002 Transparent-textarea syntax shader over heavyweight code editor libraries (2026-11-02, status: accepted)
**Context:** The Code pane needs syntax color hints and Stage-selected line highlighting for HTML, CSS, and JS without pulling in Monaco or CodeMirror (P1-04, P2-01).
**Decision:** Use Plainchant's transparent `<textarea id="editor">` backed by a synchronized `<div class="editor-shade">` (`src/code-shade.js` + `src/app/shade.js`), including a wrap-alignment check (`checkShade`) and `.sh-selected-line` range highlighting (`highlightCodeRange`).
**Alternatives:** Monaco or CodeMirror 6 (rejected: megabytes of bundled JS and incompatible with the zero-dependency rule in D-001).
**Consequences:** Font metrics and padding between `#editor` and `.editor-shade` must stay synchronized via `copyEditorType`. The coloured copy must contain exactly the editor's characters: `CodeShade.shade` replaces any line whose runs do not re-join to the source with an uncoloured line (`kind: 'plain'`), and `test/project.test.js` fails if a tokenizer ever needs that fallback on the repository's own files. When `checkShade` still detects a wrap mismatch, colours stay off until reload or until **Syntax colours** is toggled in Settings, and a notice says so (amended 2026-11-02 after self-closing tags were found to drop their `/`).

## D-003 Non-destructive byte-offset AST splicing for round-trip HTML and CSS editing (2026-11-02, status: accepted)
**Context:** Visual WYSIWYG editors often serialize `innerHTML` from the live DOM back to source, destroying user formatting, indentation, comments, and attribute order (P1-01, P1-02).
**Decision:** All visual edits on the Stage and in the Inspector go through `src/html-ast.js` and `src/css-ast.js`, which record exact character offsets (`start`, `end`, `openStart`, `openEnd`, `closeStart`, `attrSpans`) and splice only the modified byte range in the source string.
**Alternatives:** Serializing `stageFrame.contentDocument.documentElement.outerHTML` (rejected: strips formatting, injects runtime bridge attributes into source, and mangles whitespace).
**Consequences:** `HtmlAst.stamp` injects `data-pc-id` attributes only into the ephemeral preview document sent to `stageFrame.srcdoc`, never into the user's source buffer.

## D-004 Multi-file project serialization in IndexedDB via sentinel markers (2026-11-02, status: accepted)
**Context:** Reuse Plainchant's battle-tested IndexedDB `Store`, `Library`, and `Versions` modules (which expect a single `content` string per record) for multi-file web projects (P1-03).
**Decision:** `Project.pack` and `Project.unpack` (`src/project.js`) serialize all text files in `projectFiles.entries` (plus directory tree metadata) using `/* === PLAINCHANT:FILE:<path> === */` markers inside `record.content`.
**Alternatives:** Redesigning the IndexedDB schema with a separate files object store (rejected: breaks direct compatibility with `Store`, `Library`, and `Versions` snapshot diffing).
**Consequences:** Whole-project snapshots and 30-day trash recovery work across arbitrarily many `.html`, `.css`, and `.js` files out of the box.

## D-005 Tauri v2 desktop wrapper with staged `src-tauri/dist` build directory (2026-11-02, status: accepted)
**Context:** Pointing `frontendDist` in `src-tauri/tauri.conf.json` to `..` caused `tauri::generate_context!()` to recursively scan `src-tauri/target/`, making builds take minutes (P3-01).
**Decision:** `src-tauri/build.rs` copies only the static frontend files (`index.html`, `app.html`, `manifest.webmanifest`, `sw.js`, `src/`, `fonts/`, `icons/`) into `src-tauri/dist/` before compilation, and `frontendDist` points to `"dist"`.
**Alternatives:** Pointing `frontendDist` to `..` (rejected: recursive scan of `src-tauri/target/` stalls builds).
**Consequences:** Incremental `cargo build` completes in ~1 second; `src-tauri/dist/` is gitignored and refreshed automatically on every `cargo build`.

## D-006 Isolated Studio project environment for opened folders and localhost asset server (2026-11-02, status: accepted)
**Context:** Real project folders (such as multi-page portfolios) use custom stylesheet names (`style.css`), multiple HTML pages, subdirectories, and relative binary images (`images/gallery/*.jpg`). Furthermore, users expect opening an existing folder to create a safe Studio project workspace rather than silently overwriting their disk files on auto-save (P3-01, P3-02, P3-03).
**Decision:**
1. In Tauri, `open_project_folder` recursively loads text files into `projectFiles.entries` and spawns a localhost HTTP asset server (`127.0.0.1:<port>`) injected via `<base href>` in `Project.assemblePreview` so relative images, fonts, and stylesheets render accurately.
2. Opening a folder creates a new project environment (`currentScriptId = newId()`) in the Studio library. Auto-save and `Ctrl/Cmd+S` save only to the Studio workspace; local disk is untouched until the user explicitly triggers **Export**, which writes all project files back to disk while retaining the existing folder and file structure.
**Alternatives:** Auto-writing to disk on every 1.5s auto-save (rejected: risks unintended modifications to existing projects before the user is ready to export).
**Consequences:** `#file-bar` and `#export-modal` clearly distinguish between the Studio working copy and exporting to local disk.

## D-007 Dockable, collapsible, hideable, and floating Inspector with computed style telemetry (2026-11-02, status: accepted)
**Context:** A fixed bottom Inspector takes up vertical Stage space and only showed rules declared literally in `styles.css` (P2-02).
**Decision:** Support four Inspector states (docked, collapsed header-only, floating draggable window, and hidden via `Ctrl/Cmd+Shift+I`), stream `getComputedStyle` + bounding-box dimensions from the Stage iframe on selection, render amber margin and emerald padding overlays on the Stage, and provide **Go to CSS ↗** (`CssAst.findRuleBySelector`) to jump directly to the rule in the Code editor.
**Alternatives:** Fixed-only bottom panel (rejected: cramps Stage viewport on smaller screens).
**Consequences:** Inspector layout preferences persist in `localStorage`.

## D-008 Pointer-based Stage drag-and-drop and single-pass AST move (2026-11-02, status: accepted)
**Context:** Native HTML5 `draggable="true"` / `dragover` / `drop` inside the Stage iframe aborted drops in WebKitGTK when releasing over margins or dragging links/buttons, leaving the `[data-pc-drop-target]` guide line stuck, and two-pass `insertElement` + `removeElement` suffered from shifting `pc-id` sequence numbers (P2-03).
**Decision:** Replace HTML5 drag events on the Stage with deterministic pointer tracking (`mousedown` / `mousemove` / `mouseup` in `src/app/stage.js`) with sibling-container target resolution, and perform `HtmlAst.moveElement` as a single-pass byte-offset splice.
**Alternatives:** Native HTML5 Drag-and-Drop API (rejected: unreliable across WebKitGTK and iframe boundaries).
**Consequences:** Releasing the mouse button anywhere after a drag guide line appears reliably reorders the element and clears all drop indicators.

## D-009 Focus-preserving Stage selection and single-click inline WYSIWYG text editing (2026-11-02, status: accepted)
**Context:** Clicking an element on the Design Stage previously scheduled `editor.focus()` and selected the HTML tag in `<textarea id="editor">`, causing subsequent keystrokes to overwrite the HTML element in the Code editor instead of editing text on the Design Stage (P2-04).
**Decision:** Clicking on the Design Stage highlights the element's code lines (`.sh-selected-line`) and scrolls the Code editor without focusing `#editor`. Clicking any text-editable leaf element on the Stage immediately activates `contenteditable="true"`, places the text caret at the click coordinates (`caretRangeFromPoint`), and streams live `pc-inline-input` updates to the Code editor (`skipStageRender: true`) without reloading the Stage iframe mid-typing.
**Alternatives:** Requiring double-click to edit text and focusing the code editor on single click (rejected: breaks natural WYSIWYG typing instinct and risks accidental tag deletion).
**Consequences:** Users can click and type directly in the Design View while watching the highlighted HTML code update in real time; dragging a text element while in edit mode uses the `⠿` handle on the floating stage badge.

## D-010 Project-wide multi-file Undo and Redo stack (2026-11-02, status: accepted)
**Context:** Native `<textarea>` undo resets whenever the user switches file tabs (`editor.value = ...`) and does not capture Stage or Inspector edits to non-active files (P2-05).
**Decision:** Maintain an explicit project-wide `undoStack` and `redoStack` (up to 150 snapshots in `src/app/typing.js`) capturing `projectFiles.entries`, `activeFile`, `activeHtmlFile`, `selectedPcId`, and cursor/scroll state, coalescing rapid typing into 600ms bursts while recording discrete checkpoints for every Stage and Inspector action.
**Alternatives:** Relying on browser `document.execCommand('undo')` (rejected: fails across multi-file tab switches and cross-file CSS Inspector edits).
**Consequences:** `Ctrl/Cmd+Z` and `Ctrl/Cmd+Shift+Z` / `Ctrl+Y` (and toolbar `#undoBtn` / `#redoBtn`) work uniformly across Code, Stage, and Inspector.

## D-011 Live JS console bridge injected by `Project.assemblePreview` (2026-11-02, status: accepted)
**Context:** Developers need runtime output from the Stage without opening browser devtools (P5-01). The Design bridge is Design-only and Design mode strips scripts, so Live JS had no channel back to the Studio.
**Decision:** In Live JS mode `Project.assemblePreview` injects `Project.consoleBridge` as the first script in the preview. It wraps `console.log/info/warn/error`, `window.onerror`, and `unhandledrejection`, serialising arguments to strings and posting `{ type: 'pc-console', level, args, line, source, time }` to the parent. `assemblePreview` records where each user script starts in the final document so error lines map back to project files. The old `try/catch` wrapper and `pc-runtime-error` message are removed; the console replaces them. The console clears on every Stage re-render because scripts re-run.
**Alternatives:** Keeping the `try/catch` wrapper (rejected: loses line numbers and makes top-level `let`/`const` block-scoped, unlike a real page); parsing `Error.stack` for lines (rejected: format differs between WebKitGTK and Chromium).
**Consequences:** Console output exists only in Live JS mode; Design mode shows a hint. Line numbers rely on the document-relative `lineno` reported for inline scripts. Verified in Chromium only; WebKitGTK (Tauri on Linux) is unverified.

## D-012 Link navigation: Live JS bridge decides, the Studio resolves (2026-11-02, status: accepted)
**Context:** Clicking a relative link in the Stage iframe would navigate the `srcdoc` frame away from the Studio's active document (P5-02).
**Decision:** In Live JS mode a click bridge (`buildLiveBridgeScript`, `src/app/stage-live.js`) calls `preventDefault` on clicks that no page script already handled, for links that are not `#anchor`, scheme (`http:`, `mailto:`, `javascript:`, ...) or `//` links, and posts `pc-navigate`. In Design mode the click handler posts `pc-navigate` on `Ctrl/Cmd+Click`, and the badge and Properties panel post `pc-follow-link` / call `followProjectLink`. The Studio resolves the target with `Project.resolveRelativePath` (strips `?query` and `#hash`, decodes `%20`, clamps `..` at the project root, maps a trailing `/` to `index.html`) and opens it with `openFileInEditor` only if it is an `.html` file in `projectFiles.entries`; otherwise it shows a notice. Plain Design click is unchanged (D-009).
**Alternatives:** Intercepting only `.html` hrefs in the iframe (rejected: the iframe cannot see project files, and a missed link would navigate the Stage away); adding the bridge to `stage.js` (rejected: file is near the 500-line cap, D-001).
**Consequences:** In Live JS mode every relative non-anchor link is captured, including links to non-HTML files, which now show a notice instead of navigating. A link's `#hash` is dropped, so the target page opens at the top. Same-page `#anchor` links, empty links, `?query` links, and form submits are also cancelled in Live JS mode (the `srcdoc` Stage resolves them against the app page, which loaded a second editor in the Stage); anchors are scrolled to by the bridge, and `:target` CSS does not apply. `Project.resolveRelPath` (used by the preview) is unchanged and still differs from `resolveRelativePath` for edge cases such as `..` at the root.

## D-013 Binary project assets as Blobs in a separate IndexedDB store (2026-11-02, status: accepted; amends D-004)
**Context:** In the browser build, opening a folder loaded only text files, and the `srcdoc` Stage resolves relative URLs against the app's own origin, so project images, fonts, and CSS backgrounds never rendered (P7-09). The Tauri build is unaffected because it serves files over a localhost HTTP server (D-006).
**Decision:** On browser folder open, non-text files up to 25 MB each and 200 MB per project are kept as Blobs (`projectAssets` in `src/app/assets.js`) and saved in a new `assets` object store (`DB_VERSION` 2, keyed by script id and path). `Project.assemblePreview` takes an `assetUrls` map and rewrites relative references to `blob:` URLs: `src`, `srcset`, `poster`, and `<link href>` in tags (not `<a href>`), and CSS `url()` in HTML and in inlined stylesheets (resolved relative to the stylesheet). Larger files are skipped with a notice. Assets follow their project: copied on Duplicate, dropped when the trash purge removes a project, and exported with **Export to a new folder**. Pack format (D-004) is unchanged; binaries never enter `record.content` or snapshots.
**Alternatives:** Memory only (rejected: images vanish on reload); persisting the folder handle (rejected: permission prompt on every reload and ties the project to the disk copy, against D-006).
**Consequences:** Snapshots and Restore do not version binaries; a restored snapshot uses the project's current assets. Images set from user JS (`img.src = 'images/x.png'`) are not rewritten. Adding images to a project by import or drop is not supported yet (P7-02).

## D-014 Shared page parts as marker regions that keep pages plain HTML (2026-11-02, status: accepted)
**Context:** Reusing a header or footer across pages normally needs includes or a build step, which would stop `.html` files being the single source of truth (P7-10, D-003). The maintainer chose the Dreamweaver "Library Item" model over an include directive.
**Decision:** A part is an ordinary project `.html` file. A page holds a region `<!-- pc:part src="<path>" -->` ... `<!-- /pc:part -->` containing a full copy of the part; `src` is resolved relative to the page with `Project.resolveRelativePath`. `src/parts.js` finds regions, reports each as `synced`, `differs`, or `missing` (plus unmatched or nested markers), and rewrites only the text between the markers, keeping the region's indentation. Editing a part file syncs every region that references it (`propagatePartEdits` in `render`, so it is one undo step with the edit). A page whose copy differs offers **Use part** (overwrite the region) or **Update part** (make the part match and sync all other pages). **Make Part…** moves the selected element into a new part file and leaves a region behind; **Insert** adds a region for an existing part. Nested regions, and regions inside part files, are not supported.
**Alternatives:** An include directive expanded at preview/export (rejected: files on disk would not be valid standalone pages, against D-003); web components or `fetch` at runtime (rejected: needs JavaScript and a server).
**Consequences:** Pages carry duplicated markup and two comment lines per part, and exported sites work without the Studio. Syncing a part overwrites local edits made inside a region without asking (it is undoable). Opening a part file makes it the previewed HTML, so the Stage shows the fragment alone. Files under `parts/` are the suggested location; any `.html` file can be a part.

## D-015 Line-number gutter measured from a hidden mirror; find highlights on a separate layer (2026-11-02, status: accepted)
**Context:** The code editor is a transparent `<textarea>` with soft wrapping (D-002), so line numbers must line up with wrapped lines, and search needs visible matches (P6-01).
**Decision:** `#editorGutter` (in `src/app/shade.js`) draws one row per logical line and gets each row's height by laying the lines out in a hidden copy of the editor (`copyEditorType`), redrawn on a 16 ms timer after edits and resizes. Above 4000 lines it assumes no wrapping to stay fast. Search is plain text (not regex) over the current file only, implemented by `Finding` (`src/finding.js`) and `src/app/find.js`; matches are drawn as `<mark>` elements on a transparent `.editor-find` layer under the text, capped at 2000 marks. Replace and Replace All go through `applyEdit` with `Editing.diffEdit`, so they are project-wide undo steps (D-010).
**Alternatives:** Reading wrapped heights from `.editor-shade` spans (rejected: the shade is off when syntax colours are disabled or broken); marking matches inside `.editor-shade` (rejected: same dependency, and it would mean splitting highlighted runs); `requestAnimationFrame` redraws (rejected: they never fire in a hidden pane, and a timer is enough).
**Consequences:** Pressing `Ctrl/Cmd+Z` while the cursor is in the find box undoes inside that box; use the toolbar undo button or press `Esc` first. Files over 4000 lines show uniform row heights when they contain wrapped lines. Regex and project-wide search are not part of this change (`P7-05`).

## D-016 Inspector docking: five positions chosen from a menu, attached to the Stage pane (2026-11-02, status: accepted; extends D-007)
**Context:** The Inspector could only dock at the bottom of the Stage or float (D-007). The maintainer asked for top, left, and right docks too.
**Decision:** `#canvasBody` wraps the Stage viewport and the Inspector so CSS can place the panel by `data-dock` (`bottom`, `top`, `left`, `right`, `float`); the dock stays inside the Stage pane, so the code editor keeps its size. A **Dock** menu in the Inspector header (`#dockMenu`, a fixed-position `.ctx-menu` so a floating or narrow panel cannot clip it) replaces the Float button. Left and right docks are a single-column panel with a drag/keyboard resizer (`#inspectorResizer`) clamped to 240-640px and to the Stage pane width minus 200px. Top and bottom keep the content-sized, wide layout (max height 250px). The dock and side width persist in `localStorage['plainchant_web_settings']` (`inspectorDock`, `inspectorWidth`). The floating window's position is not saved.
**Alternatives:** Docking to the edges of the whole window (rejected by the maintainer: it takes width from the code editor); drag-to-snap docking (rejected by the maintainer: more code and a greater risk on WebKitGTK, D-008).
**Consequences:** A collapsed side dock shrinks to its header at the top of the column. Top and bottom docks cannot be resized (they size to their content). On narrow windows the Stage can be reduced to 200px by a side dock.

## D-017 Explorer file operations rewrite links; dirty means "changed since last explicit save" (2026-11-02, status: accepted)
**Context:** P6-02 asked for Rename, Duplicate, and Delete in the Explorer and per-file unsaved dots. Renaming a stylesheet or page without touching the links to it silently breaks the project, and auto-save (every 1.5 seconds) would clear a dot almost immediately.
**Decision:** `Project.renameFile` moves a file in place in the file list and rewrites references to it in `.html` and `.css` files (`href`, `src`, `poster`, CSS `url()`, and `pc:part src` markers), keeping `?query`, `#hash`, and root-relative style; it also re-points the moved file's own relative links so they still reach the same targets. Only references to known project files are touched (text entries plus the folder tree's binary files); scripts are not rewritten. Names are normalized and rejected if they contain `.`/`..` parts, forbidden characters, or differ from an existing file only by case. `Project.duplicateFile` names the copy `<name>-copy.<ext>` (then `-copy-2`), and `Project.deleteFile` refuses to remove the last `.html` file. Each operation is one project-wide undo step (D-010); undo snapshots now also store the open-tab list and `projectFiles.tree`. The unsaved baseline `savedFileEntries` (`src/app/explorer-ui.js`) is reset on project load, explicit Save (not auto-save), and Export; a file is dirty when its text, or its existence, differs from the baseline (`FileSync.dirtyPaths`).
**Alternatives:** Rename without link updates (rejected: breaks pages and styles silently); resetting the baseline on every auto-save (rejected: dots would vanish after 1.5 seconds and mean nothing); a confirm dialog on Delete (rejected: undo is the safety net, and `window.confirm` is unverified on WebKitGTK).
**Consequences:** Dots do not mean data is unsaved in the Studio workspace (auto-save still stores it), only that it was not explicitly saved or exported. Binary files have no Explorer actions until the asset manager (`P7-02`). Rename and Make Part prompt with `window.prompt`, like New File; it has not been verified in the Tauri WebKitGTK shell. Case-only clashes are rejected even on case-sensitive file systems so exported folders work everywhere.

## D-018 Link checker: static, project-wide, errors versus warnings (2026-11-02, status: accepted)
**Context:** Pages, stylesheets, scripts, and images are referenced by relative paths, and renaming or deleting files (P6-02) or editing by hand can silently break them (P7-04).
**Decision:** `Links.createChecker()` (`src/links.js`) extracts references from every `.html` entry through `HtmlAst` (so comments are ignored) and every `.css` entry (comments blanked), caches the extraction per file text, and resolves each one with `Project.resolveRelativePath` against the project's files (text entries plus binary files from the folder tree and browser assets). References are `a`/`area` `href`, `iframe`/`img`/`video`/`audio`/`source`/`track`/`embed`/image-input `src`, `srcset`, `poster`, `link` `href`, `script` `src`, inline `style` attributes, `<style>` blocks, CSS `url()` and `@import`. External schemes, `//` URLs, `?query`-only and `#`-only links, empty values, and values with template markers (`{{`, `{%`, `<%`, `${`, `<?`) are skipped. A missing target or a path that escapes the project is an **error**; a case-only match, an extensionless link whose `.html` exists, and a `#fragment` with no matching `id` or `<a name>` (`#top` always passes) are **warnings**. The **Problems** tab re-checks 500 ms after edits and when opened, shows a badge (red when any error), and jumps to the attribute (HTML) or URL (CSS).
**Alternatives:** Checking only the active page (rejected: renames and deletions break other pages); treating every miss as an error (rejected: fragment targets and clean URLs are often created by JavaScript or the host); a regex scan of raw text (rejected: it would flag commented-out markup).
**Consequences:** URLs built in JavaScript and server-side rewrites are invisible to the checker. A project opened in the browser without a folder has no binary files, so its image references report as missing until the images are added. Fragment warnings can be false positives for ids created at runtime. There are no quick fixes yet.

## D-019 Project-wide search is a scope of the existing find bar (2026-11-02, status: accepted; extends D-015)
**Context:** `P7-05` asked for search and replace across every text file, building on the single-file find bar (P6-01, D-015).
**Decision:** The find bar gains a **Project** toggle (`Ctrl/Cmd+Shift+F` opens it on) instead of a separate panel. In project scope the query and case toggle are shared; `Finding.findInFiles` (`src/finding.js`) lists matches for every entry with line number and a shortened line preview, shown under the bar (`#findResults`, `src/app/find-project.js`) and refreshed 120-400 ms after typing or edits. Each file has a checkbox (default checked); **Replace All in Project** runs `Finding.replaceInFiles` on the checked files and commits all changes through `commitPartEntries`, so it is one project-wide undo step (D-010). Clicking a result opens the file and selects the match; the current file's matches are still highlighted by the single-file layer, and Next/Previous/Replace keep working on the open file. Matching stays literal text with an optional case toggle.
**Alternatives:** A separate Search panel or Inspector tab (rejected: duplicates the input and options, and the find bar is already where users look); regex and whole-word options (deferred: not requested, and replacement semantics need care); a confirmation dialog before Replace All (rejected: undo is the safety net, and the checkboxes and counts show the scope).
**Consequences:** Only text entries are searched (binary assets are not in `projectFiles.entries`). The list shows at most 300 rows, but every match is replaced. Replacing inside a shared-part region makes that region differ from its part until the Parts tab resolves it (D-014). A replacement also changes files that are not open, which is why the notice states the file count.

## D-020 Insert-menu drag is pointer-based and decided in the page, not in the Stage iframe (2026-11-02, status: accepted; extends D-008)
**Context:** `P7-06` asked to drag snippets from **Insert ▾** onto the Design Stage. HTML5 drag and drop is unreliable in WebKitGTK and across the iframe boundary (D-008), and the iframe cannot see the menu.
**Decision:** `src/app/insert-drag.js` listens for `pointerdown` on `.ins-btn[data-insert]`, starts a drag after 6 px of movement, closes the menu, captures the pointer on `document.body` so moves keep arriving over the iframe, and shows a ghost label. For each move it reads the Stage's own document (it is same-origin, `allow-same-origin`) with `elementFromPoint`, finds the nearest `[data-pc-id]` element, and asks `DomOutline.dropPlacement` for before, after, or inside from the pointer's vertical position (containers such as `div`, `section`, `li` accept all three; paragraphs, headings, lists, tables, and void elements only before/after; `body` and an empty area insert at the end of `body`). It marks the target with the existing `data-pc-drop-target` attribute (a dashed outline for `inside`, added to the bridge CSS) and scrolls the Stage when the pointer is within 36 px of its top or bottom. Release inserts with `HtmlAst.insertElementAt`, which also returns the new element's id so it is selected; the change is one undo step via `applyHtmlTransform`. `Escape`, `pointercancel`, or releasing outside the Stage cancels. Only Design mode accepts drops; Live mode shows a hint. A press without movement still behaves as a normal click.
**Alternatives:** HTML5 `draggable` / `dragover` (rejected: D-008); a bridge script inside the iframe receiving `postMessage` positions (rejected: more moving parts when the page can read the Stage document directly); dropping only inside the selected element (rejected: the guide must follow the pointer).
**Consequences:** The page depends on the Stage being same-origin; a future sandbox change would break the drag. If the Stage is re-rendered mid-drag its element ids can briefly disagree with `currentHtmlAst`. Drags from the right-click Insert flyout are not supported. Real mouse and WebKitGTK behaviour is unverified.

## D-021 Pseudo-states are edited as `<base>:<state>` rules and previewed by rewriting selectors in the Design Stage (2026-11-02, status: accepted; extends D-007)
**Context:** `P7-07` asked for `:hover`, `:focus`, `:active`, and similar rules to be editable in the CSS Designer and previewable. A browser cannot be told to apply `:hover` to an element, and the source CSS must not be altered (D-003).
**Decision:** The CSS Designer's target list shows base selectors only (`CssAst.baseSelector` strips trailing `:hover`, `:active`, `:focus`, `:focus-visible`, `:focus-within`), and a **State** bar chooses the state. The rule being read and edited is `CssAst.withState(base, state, element)`, which appends the state to the part of a grouped selector that matches the selected element; the rule is created on the first change, like any other target. Typing a selector that ends in a state (for example `.card:hover`) selects that state and base. To preview, design-mode previews pass `forceStates` to `Project.assemblePreview`, which rewrites a copy of every linked stylesheet and `<style>` block with `CssAst.forceStates`: each selector that contains a supported pseudo-class gains a twin where the pseudo-class is replaced by `[data-pc-force~="<state>"]` (same specificity, same order). The Stage bridge sets `data-pc-force` on the selected element, and on its ancestors for `hover`, `active`, and `focus-within` (`active` also implies `hover`; `focus` implies `focus-within`), so rules like `.card:hover .title` preview too. Changing the state posts `pc-force-state` to the bridge without reloading the Stage; the attribute exists only in the preview document, never in the project. Computed-style placeholders then show the forced state's values. The state persists when selection changes, is ignored for inline styles, and the preview is off in Live JS mode (where real hover works).

## D-030 Format: conservative per-language formatters in one pure module (2026-11-03, status: accepted)
**Context:** `P7-14` asked for a way to format the current file. A runtime dependency such as Prettier is ruled out (D-001), and an incorrect formatter would silently change user code.
**Decision:** `src/format.js` (UMD, no DOM) exposes `formatHtml`, `formatCss`, `formatJs`, `byPath`, and `detectIndent`. Each tool only changes whitespace, except CSS, which also adds a trailing `;` to the last declaration and a space after `:` and `,`. CSS is a single pass over characters that tracks strings, parentheses, and comments. HTML is a tokenizer plus an indent stack: only a fixed list of block elements opens a level, everything else is an inline run joined with collapsed whitespace; a block that holds a single short inline run stays on one line (limit 120); `pre`, `textarea`, and non-JS `script` bodies are verbatim; end tags that HTML lets you omit (`li`, `p`, `td`, and similar) close implicitly. JavaScript is **re-indentation only**: it counts `{ ( [` nesting outside strings, comments, regex literals, and template literals (including `${}`), never touches lines that begin inside a multi-line string or template, and does not add or remove tokens. The indent unit is detected from the file (`Format.detectIndent`). `src/app/format-ui.js` replaces the buffer with `Editing.diffEdit` and `applyEdit`, so it is one undo step, from a **Format** button and `Alt+Shift+F`.
**Alternatives:** A full JavaScript pretty-printer (rejected: needs a real parser to be safe with ASI, regexes, and JSX-like text, and cannot be a no-dependency one-file module with guarantees); JSON formatting (rejected: `JSON.stringify` would drop duplicate keys and rewrite number text); wrapping long lines (deferred: needs per-language rules); formatting on save (rejected: changes user files without being asked).
**Consequences:** Formatting an inline-block layout whose siblings had no whitespace between them adds a gap. HTML whitespace between inline siblings is kept as one space. JavaScript chains and ternaries lose any extra hand-made indentation, because only nesting depth is used. The regex-versus-divide guess follows the previous token and can be wrong in rare code, which affects only indentation of that file. `.svg` and other types are not offered.

**Alternatives:** A hand-written facsimile of Prism's grammars (rejected: re-typing its regex grammars invites transcription errors and gives up the tested versions the change is for); fixing the home-made tokenizer in place (rejected: it needs the same multi-line, nested, and embedded-language state Prism already has); a bigger editor such as CodeMirror or Monaco (still rejected, D-001); installing Prism through npm at build time (rejected: there is no build step).
**Consequences:** D-001 and AGENTS.md now read "zero runtime dependencies except vendored Prism". The exception is one unmodified file with a licence, not a package manager dependency, and there is still no build step. Colours are now consistent with Prism's grammars, so some tokens differ from before (for example `=` in attributes is punctuation, `&amp;` is a number-coloured entity, `url(...)` is a string). Prism's regexes can be slow on adversarial input: a 60,000-character run of unclosed `<a ` took about 3 seconds in Node, and a 250,000-character single-line minified script about 1 second, which the size limit now cuts off at 150,000 characters. Updating Prism means replacing one file and running the tests. Only the three languages the editor already coloured are included.
