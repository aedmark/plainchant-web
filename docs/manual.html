Zero-build vanilla JS & UMD architecture

#
architectureinvariantD-001

Pure domain modules in src/.js pair with classic browser scripts in src/app/.js without a bundler.

What it does

Runs directly in any modern browser (app.html) or inside the Tauri v2 desktop shell with zero frontend build tools and zero npm runtime dependencies.

How it works

  1. 12 pure UMD modules in src/*.js expose stateless parsers, bundlers, and storage helpers that run identically in the browser and in Node.js unit tests (test/run.js).
  2. 19 classic <script> files in src/app/*.js share a single global scope in app.html (core.js first, main.js last).
  3. test/structure.test.js verifies script load order, no duplicate top-level declarations, a 500-line ceiling per src/app/*.js file, and Service Worker APP_FILES parity.

Why it works this way

Recorded in D-001: avoiding Vite/Webpack/React eliminates build-step fragility, keeps the entire studio inspectable as plain files, and allows instant unit testing in Node.js without DOM shims.

Evidence
  • Studio entrypoint app.html
  • Structural invariants test test/structure.test.js
  • Architectural decision D-001 docs/DECISIONS.md

Non-destructive HTML5 and CSS byte-offset splicing

#
parserastD-003

Visual edits splice exact character spans in user source files instead of serializing live DOM innerHTML.

What it does

Parses HTML5 (HtmlAst) and CSS (CssAst) into offset-indexed syntax trees and performs surgical edits (setAttr, setText, insertElement, moveElement, duplicateElement, setProperty) while keeping user formatting, indentation, and comments intact.

How it works

  1. HtmlAst.parse() records exact start, end, openStart, openEnd, closeStart, and attrSpans character offsets plus line numbers for every element.
  2. HtmlAst.stamp() injects ephemeral data-pc-id and data-line attributes only into the preview HTML sent to #stageFrame, never into projectFiles.entries.
  3. CssAst.parse() indexes rules and declarations with exact byte ranges so Inspector edits and findRuleBySelector() modify only the targeted declaration.

Why it works this way

Recorded in D-003: serializing stageFrame.contentDocument.documentElement.outerHTML would destroy author whitespace, reorder attributes, and leak runtime bridge markers into user files.

Evidence
  • HTML5 AST & splicer src/html-ast.js
  • CSS AST & splicer src/css-ast.js
  • HTML AST unit tests test/html-ast.test.js
  • CSS AST unit tests test/css-ast.test.js

Focus-preserving Stage selection & single-click text editing

#
stagewysiwygD-009

Clicking an element on the Design Stage highlights its code block while keeping keyboard focus in the Stage for direct text editing.

What it does

Allows users to click any text element (h1-h6, p, span, a, button, li, td, etc.) on the Design Stage and immediately type or edit text in place while watching the corresponding HTML code block highlight and update live in the Code pane.

How it works

  1. Clicking on the Stage sends { type: 'pc-select', id } to the parent window, which calls selectElementById(id, { scrollEditor: true, focusEditor: false }) so #editor scrolls and highlights .sh-selected-line without stealing keyboard focus.
  2. In src/app/stage.js, clicking a text-editable element immediately activates contenteditable="true" and positions the caret at the pointer coordinates via caretRangeFromPoint.
  3. Keystrokes inside the Stage emit pc-inline-input, which splices the updated text via HtmlAst.setText() with skipStageRender: true so the iframe DOM is not blown away mid-typing.

Why it works this way

Recorded in D-009: focusing #editor on Stage click caused subsequent keystrokes to overwrite the selected HTML block in Code mode rather than editing the text naturally on the Design Stage.

Evidence
  • Stage iframe bridge src/app/stage.js
  • Selection & code scroll sync src/app/layout.js
  • Decision D-009 docs/DECISIONS.md

Pointer-based Stage drag-and-drop & badge quick actions

#
stagedrag-and-dropD-008

Deterministic pointer tracking reorders elements before, after, or inside targets with live amber drop guides.

What it does

Reorders elements on the Design Stage by dragging any element (or dragging the ⠿ handle on the floating stage badge while text editing), and provides one-click badge buttons for Move Up (↑), Move Down (↓), Duplicate (⧉), and Delete (✕).

How it works

  1. Tracks mousedown, mousemove, and mouseup inside the Stage bridge (src/app/stage.js) with a 5px movement threshold.
  2. Computes whether the pointer is in the top 28% (before), bottom 28% (after), or middle (inside for containers, otherwise nearest edge) of the hovered target, drawing [data-pc-drop-target] guide lines.
  3. On mouseup, posts pc-move-to to the parent window, which executes a single-pass byte-offset splice in HtmlAst.moveElement().

Why it works this way

Recorded in D-008: native HTML5 draggable="true" / dragover / drop events inside an iframe[srcdoc] abort drops on Linux WebKitGTK when releasing over margins or dragging links/buttons, and two-pass insert+remove shifts data-pc-id numbering.

Evidence
  • Stage pointer drag handler src/app/stage.js
  • Single-pass AST move src/html-ast.js
  • Move & duplicate unit tests test/html-ast.test.js

Dockable / floating Inspector & Rich CSS Designer

#
inspectorcssD-007

Inspects HTML attributes, live getComputedStyle values, visual box-model overlays, and jumps to CSS rules.

What it does

Provides an HTML Properties editor and a 5-section Rich CSS Designer (Layout, Spacing & Box Model, Size, Typography, Background & Border) that can be docked at the bottom, top, left, or right of the Stage from its Dock menu (side docks are a resizable single column), collapsed to its header bar, popped out as a draggable floating window, or hidden (Ctrl/Cmd+Shift+I).

How it works

  1. When an element is selected on the Stage, the bridge reads window.getComputedStyle(el) and getBoundingClientRect() and posts them to src/app/inspector-ui.js.
  2. Inputs display live computed values as placeholders while editing either inline style (HtmlAst.setAttr) or linked stylesheet rules (CssAst.setProperty).
  3. A State bar (Normal, :hover, :focus, :active, :focus-visible, :focus-within) switches the designer to the matching <selector>:<state> rule and previews it on the selected Stage element: the preview copy of each stylesheet gets [data-pc-force~="state"] twins of its pseudo-class selectors (CssAst.forceStates()) and the bridge sets data-pc-force (D-021).
  4. A Breakpoint bar (All sizes, ≤ 768px, ≤ 375px) passes a media argument to CssAst.getDeclarations(), findRuleBySelector(), and setProperty(), which create or edit rules inside the matching @media (max-width: …) block (kept in cascade order) while src/app/css-media.js resizes the Stage so the real query applies (D-026).
  5. When the selected element is display: flex or grid, a second bridge script (src/app/stage-layout.js, built around the pure src/layout.js) draws grid track guides and amber gap handles between items; dragging a handle previews the new gap and writes gap, column-gap, or row-gap through applyCssPropertyChange() (D-025). A Layout group in the designer sets direction, wrap, justify, and align-items.
  6. Hovering or editing Box Model inputs draws amber margin and emerald padding overlays on the Stage; clicking Go to CSS ↗ locates the rule via CssAst.findRuleBySelector() and highlights it in the Code editor.

Why it works this way

Recorded in D-007, D-016, and D-021: real-world stylesheets often define rules across multiple selectors or external defaults; surfacing getComputedStyle alongside declared CSS rules and allowing floating/collapsible panel states keeps the Stage spacious and informative.

Multi-page link navigation on the Stage

#
stagenavigationD-012

Following a relative link on the Stage opens the linked project page in the Studio.

What it does

In Live JS mode a normal click on a relative link opens the linked .html file in the Studio. In Design mode Ctrl/Cmd+Click, the Follow ↗ badge button, or Follow Link ↗ in Properties does the same, while a plain click still selects and edits the link text.

How it works

  1. The Live bridge in src/app/stage-live.js cancels clicks on relative, non-anchor links that page scripts did not handle and posts pc-navigate; Design-mode actions post pc-navigate or pc-follow-link.
  2. Project.resolveRelativePath(fromFile, rawHref) normalizes ./, ../, ?query, #hash, and encoded paths, and returns nothing for http:, mailto:, tel:, javascript:, data:, //, or same-page anchors.
  3. followProjectLink() opens the target with openFileInEditor() only when it is an .html file in the project; otherwise it shows a notice.

Why it works this way

Recorded in D-012: the iframe cannot see project files, so it only cancels navigation and the Studio decides, which keeps the Stage from navigating away from the active document and keeps D-009 text editing intact.

Evidence
  • Path resolver src/project.js
  • Live bridge and link handlers src/app/stage-live.js

Binary project assets in the browser build

#
assetsbrowserD-013

Images, fonts, and other binaries from an opened folder render on the Stage and survive reload.

What it does

When a folder is opened in a Chromium browser, non-text files (up to 25 MB each, 200 MB per project) are kept with the project so relative src, srcset, poster, <link href>, and CSS url() references display on the Stage. The desktop app does not need this because it serves files over localhost.

How it works

  1. scanBrowserDir() in src/app/tauri-files.js collects binaries as Blobs; src/app/assets.js creates blob: URLs and saves the Blobs to the IndexedDB assets store keyed by project.
  2. Project.assemblePreview() rewrites matching relative references through Project.rewriteAssetUrls() and rewriteCssUrls(); stylesheet URLs resolve relative to the stylesheet file.
  3. Assets are loaded again when the project opens, copied on Duplicate, removed when the trash purge deletes the project, and written by Export to a new folder.

Why it works this way

Recorded in D-013: the srcdoc Stage resolves relative URLs against the app origin, and persisting Blobs separately keeps the single-string pack format of D-004 and the isolated workspace of D-006.

Shared page parts (marker regions)

#
partsreuseD-014

Reuse a header or footer across pages while every page stays plain HTML.

What it does

Make Part… moves the selected element into a project file such as parts/header.html and leaves a <!-- pc:part src="..." --> region in the page. Pages can include the same part, editing the part file updates all of them, and the Parts Inspector tab lists parts, flags pages whose copy differs, and inserts a part into the current page.

How it works

  1. src/parts.js finds marker regions in every .html entry, resolves src with Project.resolveRelativePath, and reports each region as synced, differs, or missing; unmatched or nested markers are reported and never rewritten.
  2. propagatePartEdits() runs inside render(): when the active file is a part, Parts.sync() rewrites only the text between markers in every page that references it, in the same undo step as the edit.
  3. A page that differs from its part offers Use part (overwrite the region) or Update part (Parts.pull() makes the part match, then syncs every other page).

Why it works this way

Recorded in D-014: duplicating the part inside each page keeps every file valid standalone HTML (D-003) with no include directive or build step, at the cost of duplicated markup and syncing that overwrites local edits made inside a region.

Evidence
  • Region finder and synchronizer src/parts.js
  • Parts tab and Make Part src/app/parts-ui.js

Line-number gutter and Find / Replace

#
editorfindD-015

Line numbers that follow wrapped lines, plus in-file and project-wide find and replace with undo.

What it does

The code editor shows line numbers (highlighting the caret line and the Stage-selected block). Ctrl/Cmd+F opens a find bar that highlights every match in the current file; Ctrl/Cmd+H focuses the Replace box. Enter and Shift+Enter step through matches, Aa toggles case matching, and Replace / Replace All edit the file. The Project toggle (Ctrl/Cmd+Shift+F) lists matches in every file, lets you exclude files, and replaces across the project in one undo step.

How it works

  1. drawGutter() in src/app/shade.js lays the lines out in a hidden copy of the editor to learn each wrapped line's height, so row n lines up with line n.
  2. Finding.findAll() (src/finding.js) returns literal, non-overlapping match offsets; src/app/find.js draws them as <mark> elements on a transparent layer under the text.
  3. Replacements go through applyEdit() with a minimal Editing.diffEdit() change, so they are one undo step in the project-wide history; project scope uses Finding.findInFiles() / replaceInFiles() and commits every changed file together (D-019).

Why it works this way

Recorded in D-015: measuring from a hidden mirror and drawing matches on their own layer keeps both features working when syntax colours are off, which is the failure mode of the transparent-textarea editor of D-002.

Evidence

Asset manager and image picker

#
assetsimagesD-023D-024

Browse, add, insert, pick, rename, and delete the project's images, including CSS backgrounds, with undo.

What it does

The Assets button opens a grid of every project image with a thumbnail, folder, size, dimensions, and how many places use it. Each image can be inserted as an <img>, set on the selected <img>, or copied as a path; Browse… next to Source opens the grid as a picker. Add images… or dropping image files adds them to images/ (browser and desktop), and images can be renamed (links update) or deleted, all undoable. The CSS Designer's Bg Image field has its own Browse….

How it works

  1. ImageLib.list() merges blob assets, non-text files in the folder tree, and text .svg entries; Links.usage() counts references from pages and stylesheets.
  2. src/app/asset-ui.js renders the modal and applies actions through applyHtmlTransform(); added images go through addProjectAsset() into projectAssets and IndexedDB one asset at a time, and into the folder tree when there is one.
  3. Folder export now writes any asset that is missing from the target folder or differs in size, and the zip export includes them.
  4. Asset add, rename, and delete push undo steps: snapshots hold the asset map by reference and restoreProjectAssets() reconciles memory and IndexedDB. The desktop export sends added images to save_project_folder as base64 and never deletes files on disk.

Why it works this way

Recorded in D-023 and D-024: images are a project file type the studio could not add or choose visually; asset changes now share the project-wide undo history, and export never deletes user files.

Problems tab (broken-link checker)

#
linksproblemsD-018

Finds broken links and missing files across the whole project and jumps to each one.

What it does

The Problems Inspector tab lists dead page links, missing images, media, stylesheets, and scripts, CSS url() and @import targets, links that leave the project, case-only matches, extensionless links, and #anchor targets with no matching element. A badge shows the count (red when any is an error), and clicking a row opens the file and selects the exact attribute or URL.

How it works

  1. Links.createChecker() in src/links.js extracts references from every .html file through HtmlAst (so commented-out markup is ignored) and every .css file, caching the result per file text.
  2. Each reference is resolved with Project.resolveRelativePath against the project's files plus binary files from the folder tree; a missing target is an error, while case-only matches, extensionless links, and missing fragments are warnings.
  3. src/app/problems-ui.js re-checks 500 ms after edits and whenever the tab opens, and jumps with openFileInEditor() plus a selection of the reported range.

Why it works this way

Recorded in D-018: renames, deletions, and hand edits break links in pages other than the one being edited, and static checking catches them without running anything, at the cost of not seeing URLs built in JavaScript.

Evidence
  • Checker src/links.js
  • Problems tab src/app/problems-ui.js

Explorer file operations and unsaved dots

#
explorerfilesD-017

Rename, duplicate, and delete project files with link updates, undo, and per-file unsaved markers.

What it does

Hovering or right-clicking a file in the Explorer offers Rename, Duplicate, and Delete. Renaming or moving a file rewrites links to it (href, src, poster, CSS url(), and shared-part markers); the last .html file cannot be deleted. + Folder adds folders, and dragging a file or folder onto a folder (or the blank area for the root) moves it the same way; open file tabs can be dragged to reorder. Tabs and Explorer rows show a • when a file differs from the last load, explicit Save, or Export.

How it works

  1. Project.renameFile(), duplicateFile(), deleteFile(), and treeAfter() are pure helpers; src/app/explorer-ui.js applies them as one project-wide undo step that now also restores the tab list and file tree.
  2. FileSync.dirtyPaths() compares the current files with savedFileEntries, which is reset on project load, explicit Save (not the 1.5 second auto-save), and Export.
  3. Names are normalized and rejected if they escape the project, contain forbidden characters, or clash with another file ignoring case.

Why it works this way

Recorded in D-017: renames that left links stale would silently break pages, and clearing the dot on every auto-save would make it meaningless, so the dot tracks explicit saves and exports.

Isolated Studio project environment & localhost asset server

#
taurifilesystemsecurityD-006

Opening a local folder creates a safe Studio workspace with live binary asset rendering and explicit structure-preserving Export.

What it does

Loads an existing local website folder (including nested subdirectories, multiple .html/.css/.js files, and binary images/fonts) into an isolated Studio project environment without touching local disk until the user explicitly clicks Export.

How it works

  1. In Tauri (src-tauri/src/main.rs), open_project_folder recursively reads text files into projectFiles.entries, records the directory tree, and starts a loopback HTTP static asset server (127.0.0.1:<port>) rejecting any .. path traversal.
  2. Project.assemblePreview() injects <base href="http://127.0.0.1:<port>/<dir>/"> so relative images (images/photo.jpg), fonts, and stylesheets render faithfully in #stageFrame.
  3. In src/app/tauri-files.js, opening a folder creates a new Studio library record (currentScriptId = newId()). Auto-save writes only to IndexedDB; clicking Export → Save Project to Local Folder writes all files back to disk while retaining the folder and file structure.

Why it works this way

Multi-file IndexedDB persistence & snapshot history

#
storageindexeddbD-004

Packs all project files into sentinel-delimited bundles stored in IndexedDB with emergency localStorage fallback.

What it does

Automatically saves every project edit to IndexedDB (plainchant_web_db), supports multiple projects with 30-day soft-delete trash recovery in #library-modal, and captures point-in-time project snapshots in #versions-modal.

How it works

  1. Project.pack() and Project.unpack() (src/project.js) serialize projectFiles.entries and directory metadata into a single string using /* === PLAINCHANT:FILE:<path> === */ sentinel markers.
  2. Store (src/store.js) and src/app/persistence.js write the packed record to IndexedDB and mirror unsaved changes to localStorage['plainchant_web_emergency'] on beforeunload.

Why it works this way

Recorded in D-004: sentinel packing lets Store, Library, and Versions snapshot, diff, and restore entire multi-file websites as atomic records.
